🎯 **What:** The `timingSafeEqual` function used in `utils/security.ts` to compare authentication hashes and tokens relied on a custom XOR loop over characters.

⚠️ **Risk:** Custom JavaScript loops are susceptible to timing attacks due to V8 optimizations (e.g., branch prediction or execution time variations for operations) and early returns based on string lengths. This could potentially allow an attacker to guess authentication tokens or hashes character by character by measuring the exact response time of the login or API endpoints.

🛡️ **Solution:** Rewrote `timingSafeEqual` to be asynchronous, utilizing `crypto.subtle.digest('SHA-256', ...)` to hash both strings before comparing them. Hashing ensures both inputs are reduced to fixed-length representations and entirely mitigates length and execution time leaks. All usages of `timingSafeEqual` in the worker and tests were updated to properly `await` the new secure implementation.
